# Ассистент студента Зерокодера

RAG-ассистент по конспектам курса промпт-инжиниринга. Отвечает на вопросы строго
по базе знаний, собранной из конспектов уроков, и умеет сказать «в базе этого
нет» вместо того чтобы выдумать ответ.

Итоговый проект модуля 5 «Ассистенты с памятью: базы знаний, RAG и Relevance».

## Архитектура

Система разделена на четыре независимых конвейера, связанных артефактами на
диске, а не общими объектами в памяти:

| | Конвейер | Что делает |
|---|---|---|
| **P1** | Авторство | Страница урока или файл (PDF/HTML/DOCX) → конспект `.md` |
| **P2** | Индексация | Конспекты → очищенные чанки → векторное хранилище |
| **P3** | Запрос | Вопрос → эмбеддинг → поиск → отбор контекста → LLM → ответ |
| **P4** | Оценка | Golden set → метрики качества поиска и ответов |

Полное описание с обоснованием решений — в [docs/architecture.md](docs/architecture.md).

Конвейер запроса:

```
вопрос -> кэш ответа -> эмбеддинг -> поиск (top_k x overfetch)
       -> порог релевантности -> дедупликация -> срез top_k
       -> сборка контекста -> LLM -> ответ + источники
```

## Состояние

Реализованы **этапы 1–5**: препроцессинг, провайдеры с хранилищем, сборка
индекса, поиск с кэшированием и ответ с памятью диалога. Дальше по плану —
наблюдаемость и оценка качества.

### Этап 5: ответ и память

Системный промпт лежит отдельным файлом в [prompts/](prompts/), а не строкой в
коде: правят его чаще, чем код. Версия промпта — **хеш его содержимого**, и он
входит в ключ кэша ответов, поэтому правка правил не отдаёт старые ответы как
свежие. Номер в имени файла для этого не годится: его надо помнить поднять.

Фрагменты уезжают в сообщении пользователя, а не в системном. Корпус — конспекты
курса по промпт-инжинирингу, в нём буквально лежат образцы системных промптов и
разборы атак на них; системное сообщение — это то, что модель исполняет, и
чужому тексту там не место.

Список источников печатает программа и нумерует его так же, как фрагменты в
контексте: ссылка `[3]` в ответе обязана находиться третьей строкой. Отсюда же
берётся дешёвая проверка обоснованности — ссылка на `[7]` при пяти фрагментах
может быть только выдумкой, и она попадает в отчёт.

Память диалога живёт в сессии, `/clear` очищает её досрочно. Уточняющий вопрос
она чинит не только для модели, но и **для поиска**: у «а сколько его ставить?»
нет ни одного предметного слова, и без предыдущего вопроса в базе не находится
ничего. Признак уточнения — отсылка наружу плюс краткость: «что такое overlap и
зачем он нужен?» содержит «он», но находится сам.

Ответ, посчитанный с непустой историей, **не кешируется**: он зависит от
предыдущих реплик, а ключ кэша о них не знает. Уровни L1 и L2 от истории не
зависят и работают всегда.

На живом индексе: «а сколько его ставить?» после вопроса про overlap находит
ответ (10-20%) и показывает, чем именно искали; после `/clear` тот же вопрос
даёт девять кандидатов, все ниже порога, и честный отказ.

### Этап 4: поиск

Порядок операций: **overfetch -> порог -> дедупликация -> срез top_k**. Если
взять сразу `top_k` и потом отсечь по порогу, порог будет сокращать контекст
вместо того, чтобы улучшать его.

Пустая выдача — это ответ «в базе знаний такого нет», а не ошибка: модель в
этом случае не вызывается.

Кэш на SQLite в три уровня (PEr07): вектор запроса, результаты поиска, готовый
ответ. Параметры входят **в ключ**, поэтому смена `top_k` или фильтра корректно
промахивается мимо кэша, а не отдаёт результат, посчитанный по другим настройкам.

Порог откалиброван на корпусе: минимальное сходство у вопроса, ответ на который
в базе есть, — 0.364; максимальное у постороннего вопроса — 0.309. Зазор всего
0.055, порог стоит в его середине.

### Этап 3: сборка индекса

`index build` приводит хранилище в соответствие с конспектами. Векторизуется
только изменившееся: чанк со знакомым `content_hash` пропускается, поэтому
повторный запуск не обращается к API вообще. Отсюда же следует, что сборка
возобновляема — прерванный прогон продолжится с того места, где остановился.

На реальном корпусе: первая сборка 920 чанков за 15 секунд, повторная — 2
секунды и ноль запросов.

### Этап 2: провайдеры и векторное хранилище

- единый клиент для OpenAI и ProxyAPI — различие сводится к `base_url`, поэтому
  дублировать реализацию не нужно; контракты `LLMProvider` и `EmbeddingProvider`
  разделены, потому что смена модели генерации свободна, а смена модели
  эмбеддингов обязывает пересобрать индекс;
- векторное хранилище на ChromaDB: коллекция именуется по модели эмбеддингов,
  косинусная метрика, фильтры по метаданным, идемпотентный upsert;
- манифест индекса: несовместимость по модели — отказ, расхождение по
  параметрам чанкинга — предупреждение.

### Этап 1: препроцессинг

Что уже работает:

- разбор Markdown с учётом fenced-блоков (комментарий `#` в листинге не считается
  заголовком, пустая строка внутри ``` не рвёт блок);
- отбор секций по настраиваемому списку — служебные разделы отбрасываются,
  незнакомый заголовок сохраняется;
- очистка текста: эмодзи, HTML-теги, разметка, невидимые символы, схлопывание
  пробелов; варианты тире приводятся к одному символу, а не удаляются;
- структурный чанкинг по токенам с перекрытием целыми предложениями,
  contextual header и неделимыми листингами;
- слияние мелких соседних секций-сестёр;
- метаданные из пути, имени файла и заголовка (frontmatter, если есть,
  переопределяет выведенное).

## Установка

```bash
python -m venv .venv
```

```bash
.venv\Scripts\activate
```

```bash
pip install -e ".[dev]"
```

```bash
copy .env.example .env
```

В `.env` укажите `NOTES_DIR` — путь к папке с конспектами; она может лежать вне
проекта. Для `index preview` этого достаточно. Для `index build` понадобится
`OPENAI_API_KEY` (или `PROXYAPI_API_KEY` при `EMBED_PROVIDER=proxyapi`).

## Использование

Посмотреть, как корпус разбивается на чанки, — сводка, гистограмма размеров и
примеры:

```bash
zassist index preview
```

Только один урок, с выгрузкой чанков в JSONL:

```bash
zassist index preview --lesson PEr08 --export chunks.jsonl
```

Собрать индекс (векторизуется только изменившееся):

```bash
zassist index build
```

Посмотреть план сборки, ничего не тратя:

```bash
zassist index build --dry-run
```

Что лежит в индексе и чем он собран:

```bash
zassist index stats
```

Найти фрагменты по запросу (без обращения к языковой модели):

```bash
zassist search "как работает кэширование в RAG"
```

Поиск в пределах одного урока:

```bash
zassist search "оценка качества" --lesson PEr06
```

Ответить на вопрос по конспектам:

```bash
zassist ask "как работает кэширование в RAG"
```

Показать отбор, размер контекста и тайминги:

```bash
zassist ask "что такое порог релевантности" --verbose
```

Диалог с памятью (`/clear` — забыть, `/exit` — выйти):

```bash
zassist ask --repl
```

Состояние кэша:

```bash
zassist cache stats
```

Все команды и опции:

```bash
zassist --help
```

## Структура

```
src/zerocoder_assistant/
├─ config/          настройки из окружения и предметные константы
├─ preprocessing/   разбор Markdown, очистка, чанкинг, метаданные
├─ embeddings/      поставщики эмбеддингов (OpenAI, ProxyAPI)
├─ llm/             клиенты языковых моделей
├─ vectorstore/     ChromaDB и манифест индекса
├─ indexing/        сборка индекса с идемпотентной переиндексацией
├─ retrieval/       поиск: порог, дедупликация, фильтры
├─ generation/      промпт, сборка контекста, ответ
├─ memory/          короткая память диалога
├─ cache/           кэш на SQLite в три уровня
├─ reporting.py     агрегаты и текстовые отчёты
├─ errors.py        предсказуемые отказы, отличимые от сбоев
└─ cli/             команды терминала
prompts/               системные промпты (версия = хеш содержимого)
docs/architecture.md   архитектурное решение целиком
tests/                 модульные тесты и прогон по реальному корпусу
```

Всё, что можно вынести, вынесено: пути, размеры, пороги и модели — в `.env`,
предметные списки и регулярные выражения — в `config/constants.py`. В корне
проекта только конфигурация и документация.
