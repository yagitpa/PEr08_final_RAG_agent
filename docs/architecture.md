# Архитектура: RAG-ассистент студента Зерокодера

## Context

Домашнее задание PEr08 сформулировано предельно широко: «создать готового RAG-ассистента, подключить к OpenAI API или GigaChat, прикрепить ссылку на проект». Это даёт полную свободу и одновременно означает, что качество работы определяется не выполнением чеклиста, а тем, насколько система собирает воедино весь модуль 5: препроцессинг (PEr03), память (PEr04), оценку (PEr06), кэш и параметры поиска (PEr07).

Проект из архива урока (`5-8-final.zip`) как основа непригоден: это две почти дословно продублированные папки (`assistant_api`/`assistant_giga`), плоская выкладка в корне, захардкоженные параметры, нет конфига, метаданных, порога релевантности, фильтров, загрузчиков форматов и идемпотентной переиндексации. Полезны из него ровно две идеи — кэш на SQLite и чанкинг с приоритетом абзацев. Всё остальное проектируется заново.

Корпус знаний уже существует и лежит **вне** проекта: `Homework/Конспекты/<Модуль>/PErNN_*.md` — 46 файлов, ~1.56 млн символов (~400k токенов), 7 модулей. Стоимость полной векторизации через `text-embedding-3-small` — порядка одного цента, то есть объём не является ограничением ни для экспериментов, ни для переиндексации.

Итог этапа — архитектурное решение, без кода.

## Разбор твоего варианта

Список закрывает почти все темы модуля, и большинство пунктов я беру как есть: SQLite-кэш с метаданными, порог релевантности, фильтрация по источникам, top_k и размер контекста как настройки, RAGAS, переключение провайдеров, терминал, разнесение по папкам, конфиг через окружение, промпты через `/ai-instruction-design`, деплой на GitHub.

Ниже — только то, что я меняю, и почему. Это и есть содержательная разница между вариантами.

### 1. Один «агент» → четыре независимых пайплайна

В твоём списке авторство конспекта, индексация, ответ на вопрос и оценка перечислены как способности одной сущности. Это разные процессы с разной частотой запуска, разной ценой ошибки и разными зависимостями: конспект пишется один раз на урок и требует ревью; индекс пересобирается при смене параметров чанкинга; запрос выполняется постоянно; оценка гоняется пачкой. Если это один объект, они неизбежно срастаются, и поменять размер чанка нельзя без перегенерации конспектов.

Разделяю на **P1 Авторство → P2 Индексация → P3 Запрос → P4 Оценка**, связанные через артефакты на диске (`.md` и векторное хранилище), а не через общие объекты в памяти.

### 2. Браузер — слой добычи, а не часть рантайма

Claude-in-Chrome — это MCP-инструменты, которыми управляет Claude Code, а не Python-код проекта. Если сделать «агент сам ходит в браузер» частью рантайма, проект перестанет быть воспроизводимым и самодостаточным репозиторием.

Поэтому добыча (`acquisition`) отделена от авторства (`authoring`): браузерный шаг сохраняет сырой текст урока в `data/raw/`, дальше Python-команда генерирует конспект из этого сырья. Тот же `data/raw/` наполняют загрузчики PDF/HTML/DOCX. Браузер становится одним из четырёх равноправных адаптеров добычи — тем единственным, который не может быть Python-кодом из-за авторизации.

### 3. Тире и дефисы — нормализовать, не удалять

В списке очистки есть «дефисы, тире». Удаление сломает русский текст: «что-то», «из-за», «RAG-система», диапазоны «300-500». Вместо удаления — приведение вариантов (`—`, `–`, `‑`, `−`) к одному символу. Экономия токенов нулевая, риск потери смысла реальный.

### 4. «Результат дня» — оставить, «Что мы умеем» — выбросить

Ты предлагаешь резать «цели занятия, результаты урока». Развожу эти секции:

- **`## Результат дня`** — это готовое резюме **текущего** урока. Лучший из возможных чанков для вопроса «о чём был урок PEr06». Оставляю, помечаю `content_type: summary`.
- **`## Что мы умеем`** — пересказ **предыдущего** урока. При индексации создаёт почти-дубликат содержания соседнего файла, но с чужим `lesson_id`, что напрямую ломает вопросы «в каком уроке это было». Выбрасываю.
- **Шапка «Дорогой студент!»** — идентична во всех 46 файлах. Классический дублирующийся футер из PEr03. Выбрасываю.
- **Блоки «⚠️ Актуализация»** — твои собственные проверенные поправки, самая свежая фактура в корпусе (пины версий, статусы сервисов). Оставляю и помечаю `content_type: actualization`, чтобы их можно было приоритизировать при выдаче.

Фильтр секций — **конфигурируемый список паттернов, неизвестный заголовок по умолчанию сохраняется**. Это не перестраховка: по корпусу «Домашнее задание» есть в 42 файлах из 46, «Теория на сегодня» — в 33, часть модулей нумерует разделы через `## N.` вместо `### N.`. Жёсткий список молча съест содержательные секции.

### 5. Чанкинг по структуре Markdown, а не только по абзацам

Ты описываешь плавающую разбивку по границам абзацев. Для этого корпуса есть вариант сильно лучше: у конспектов жёсткая иерархия заголовков. Базовая единица чанка — **секция**, и только переполненная секция режется по абзацам, а переполненный абзац — по предложениям.

Три добавления к твоей схеме:

- **Contextual header.** В текст чанка префиксом уходит путь заголовков: `PEr08 › Теория на сегодня › 4. Параметры RAG`. Фрагмент перестаёт быть безымянным куском текста и для эмбеддинга, и для LLM.
- **Блоки кода атомарны.** Конспекты набиты Python-листингами; разрыв внутри ``` даёт бессмысленный чанк.
- **Токены, а не символы.** У тебя корректно указано 300–500 токенов — значит нужен `tiktoken`, а не `len(str)`. В коде урока везде символы, и это расходится с заявленным размером примерно втрое.

### 6. Overfetch → порог → дедупликация → top_k

Порог релевантности в твоём списке есть, но порядок операций критичен. Если сначала взять top_k, а потом отсечь по порогу — порог просто уменьшает выдачу вместо того, чтобы её улучшать. Правильно: запросить `top_k × 3`, отсечь по порогу, дедуплицировать, взять `top_k`.

Дедупликация обязательна именно из-за твоего overlap +15%: перекрытие гарантированно порождает почти-дубликаты, и без дедупа половина контекста — повторы.

Отдельно: **если после порога не осталось ничего — вернуть отказ, не вызывая LLM**. Это и есть смысл порога. Экономит деньги и полностью снимает галлюцинацию на вопросах вне базы.

### 7. Ключ кэша = запрос + отпечаток конфигурации

Ты верно указал, что в кэш идут метаданные (top_k, фильтры). Формулирую жёстче: они должны входить **в ключ**, а не лежать рядом. Иначе смена `top_k` отдаёт старые ответы — ровно тот сценарий, который домашки модуля просят продемонстрировать.

Отпечаток: `normalized_query + top_k + threshold + filters + llm_model + embed_model + prompt_version + index_version`.

### 8. Память диалога ломает наивный кэш ответов

Следствие решения добавить историю: если ответ зависит от истории, а ключ кэша — нет, кэш начинает врать. Решение простое и корректное:

- **L1 (эмбеддинг запроса)** и **L2 (результаты поиска)** от истории не зависят → кэшируются всегда.
- **L3 (финальный ответ)** кэшируется **только когда история пуста**.

Три уровня кэша — прямо по PEr07, в одном SQLite тремя таблицами.

### 9. Индекс привязан к эмбеддеру и защищён манифестом

Главная тихая поломка RAG: индекс собран одной моделью эмбеддингов, запрос векторизуется другой. Поиск не падает — он молча возвращает мусор. В v1 провайдер один, но защита нужна сразу, иначе она не появится никогда.

Коллекция именуется по эмбеддеру (`notes__text-embedding-3-small__v1`), рядом лежит `index_manifest.json` с моделью, размерностью, параметрами чанкинга и версией очистки. На старте запроса — сверка; расхождение = внятный отказ «пересоберите индекс», а не тихая деградация.

### 10. Идемпотентная переиндексация

В коде урока переиндексация невозможна: `if collection.count() > 0: return`. Правишь конспект — изменения не попадают в базу. Вместо этого: `content_hash` на чанк, переэмбеддинг только изменённых, удаление исчезнувших.

### 11. RAGAS изолирован, лёгкая оценка — всегда

RAGAS ломает окружение — это задокументировано в твоих же блоках «Актуализация» дважды (PEr06 и PEr08), с разными рабочими наборами версий. Ставить ядро проекта в зависимость от него нельзя.

- **Встроенная оценка** (без RAGAS, работает всегда): recall@k по `lesson_id` на golden set, средняя similarity топа, корректность отказа на неотвечаемых вопросах, p50/p95 латентности, hit-rate кэша.
- **RAGAS** — отдельный модуль и отдельный `requirements-eval.txt` с пинами `ragas==0.2.15` + `langchain-community==0.3.27` (комбинация, проверенная в конспекте PEr08 под эту структуру импортов).

## Целевая архитектура

### P1. Авторство конспекта

```
[browser | html | pdf | docx] → RawDocument → data/raw/<slug>.txt
                                     ↓
                        LLM + prompts/note_author_v1.md
                                     ↓
                   data/notes/<Модуль>/<PErNN_slug>.md  (+ YAML frontmatter)
                                     ↓
                          ревью человеком → P2
```

Адаптеры добычи: `browser_handoff` (принимает текст, снятый Claude-in-Chrome), `html` (BeautifulSoup), `pdf` (pdfplumber — лучший контроль layout), `docx` (python-docx). Все возвращают единый `RawDocument{text, source_ref, source_type, fetched_at}`.

**Human-in-the-loop сознательно:** команда пишет `.md` и не индексирует. Конспект — фундамент всей системы, а его генерация недетерминирована; автоиндексация непроверенного конспекта — это ровно «мусор на входе» из PEr03.

**Frontmatter — источник метаданных для P2:**

```yaml
lesson_id: PEr08
module_num: 5
module: "Модуль 5. Ассистенты с памятью: базы знаний, RAG и Relevance"
title: "Практика: ассистент по документации"
source_url: ...
source_type: browser
notes_version: 1
```

### P2. Индексация

```
.md → parse → select → clean → chunk → embed → upsert
```

| Стадия | Содержание |
|---|---|
| `parse` | Markdown → дерево секций с `heading_path`; поддержка обоих стилей нумерации |
| `select` | Конфигурируемый фильтр секций; неизвестный заголовок сохраняется |
| `clean` | Эмодзи, HTML-теги, служебные символы, маркеры разметки, схлопывание пробелов; унификация тире; **без** lowercase (кириллица, имена моделей); блоки кода не трогаются |
| `merge` | Слияние мелких соседних секций-сестёр под общим родителем |
| `chunk` | Секция как единица → абзацы → предложения; целевой размер 300–500 токенов (`tiktoken`); overlap 15% целыми предложениями; contextual header; код атомарен |

**300–500 токенов — это цель, а не жёсткий коридор.** Секция короче целевого
размера искусственно не добивается и не выбрасывается: определение термина на
60 токенов — плотное знание, а не брак. Нижняя граница отчёта задаётся
`CHUNK_MIN_TOKENS` (по умолчанию 80) и служит для двух вещей — слияния мелких
черновиков и подсветки в статистике. Превышать `CHUNK_MAX_TOKENS` вправе только
неделимый листинг.
| `embed` | Батчи, кэш по `content_hash` |
| `upsert` | Chroma, `id = {source_file}:s{ordinal}:c{index}`, идемпотентно |

**Идентификатор чанка строится от пути файла, а не от `lesson_id`.** В корпусе
`lesson_id` не уникален: `PEnB10` носят два разных конспекта, и при upsert один
молча затирал бы чанки другого. Проверка на дубликаты встроена в отчёт.

**Мусор отсеивается по природе содержимого, а не по размеру.** Порог в токенах —
плохой прокси: он одинаково режет административную шапку урока и определение
термина, хотя первое бесполезно, а второе — самое плотное знание в базе.
Поэтому отбрасываются конкретные классы блоков (дисклеймер, название модуля,
строки «Курс / Статус / Время чтения»), а короткие содержательные фрагменты
сохраняются независимо от длины. Вред шаблонных блоков не в занятом месте, а в
том, что они почти одинаковы и конкурируют за места в `top_k` с настоящим
содержимым.

**Схема метаданных чанка** — от неё зависят фильтры, цитирование источников и оценка:

`lesson_id`, `module_num`, `module`, `lesson_title`, `heading_path`, `section_title`, `chunk_index`, `content_type` (`theory|summary|practice|code|actualization`), `source_file`, `content_hash`, `token_count`, `embed_model`, `notes_version`

### P3. Запрос

```
query → normalize
      → [L3] кэш ответа (только при пустой истории) ──hit──▶ return
      → [L1] кэш эмбеддинга запроса
      → [L2] кэш результатов поиска
      → поиск: top_k × OVERFETCH
      → порог: similarity = 1 − distance (Chroma cosine)
      → дедупликация (content_hash + близкие пары)
      → срез top_k
      → пусто? ──▶ отказ БЕЗ вызова LLM
      → сборка контекста: system + история + нумерованные чанки, обрезка по MAX_CONTEXT_TOKENS
      → LLM
      → [L3] сохранение (только при пустой истории)
      → {answer, sources[], timings{embed, search, llm}, from_cache}
```

Фильтры уходят в Chroma как `where` (`--lesson PEr06`, `--module 5`, `--content-type`).

Возврат `timings` — не украшение: он делает выигрыш кэша измеримым и закрывает тему оптимизации из PEr07 числами, а не рассуждениями.

**Уточнения, добавленные при реализации (этап 5).**

*Уточняющий вопрос ищется не так, как задаётся.* «А сколько его ставить?» модель поймёт из истории — история едет в запрос целиком. Но эмбеддинг этой фразы не найдёт в базе ничего: предметных слов в ней нет, всё содержание осталось в предыдущей реплике. Поэтому в **поисковый** запрос подмешивается тема разговора — последние *самодостаточные* вопросы, а не предыдущие по порядку. Взяв буквально предыдущий, цепочка «что такое overlap» -> «а сколько его ставить?» -> «а почему так?» на третьей реплике осталась бы вовсе без предметных слов; накапливать же всю цепочку нельзя, запрос рос бы без предела. Признак уточнения — два условия сразу: отсылка наружу (союз-связка в начале либо местоимение) **и** краткость (не больше `FOLLOW_UP_MAX_WORDS` слов). Одной отсылки мало: «что такое overlap и зачем он нужен?» содержит «он», но находится сам. Расширять запрос отдельным вызовом модели не стали — это лишний запрос на каждую реплику ради случая, который закрывается списком слов (и это прямо в списке «сознательно не делаем»).

*Фрагменты едут в сообщении пользователя, а не в системном.* Корпус — конспекты курса по промпт-инжинирингу: в нём буквально лежат образцы системных промптов, инструкции для других моделей и разборы атак на них. Системное сообщение — это то, что модель исполняет; фрагментам там не место, даже когда так короче.

*Версия промпта — хеш содержимого, а не номер в имени файла.* Номер надо помнить поднять, хеш меняется сам. Он входит в ключ L3, поэтому правка промпта промахивается мимо ответов, посчитанных по прежней редакции, вместо того чтобы месяц отдавать их как свежие.

*Бюджет контекста режется целыми фрагментами.* Обрезка чанка посередине экономит токены, но отрезает конец мысли — модель видит начало определения без сути и договаривает сама. Исключение одно: если бюджет меньше одного чанка, фрагмент урезается, потому что отдать пустоту на найденный ответ хуже.

*Проверка ссылок различает ссылку и код.* Корпус полон примеров на Python, и модель их цитирует: без просмотра назад в регулярном выражении `items[0]` и `data[42]` объявлялись бы выдуманными ссылками, а будущая метрика этапа 7 мерила бы долю ответов с кодом. При попадании в кэш ссылки пересчитываются, иначе повтор вопроса показывал бы галлюцинацию как проверенный ответ.

*Список источников печатает программа и нумерует его 1:1 с фрагментами.* Ссылка `[3]` в ответе обязана находиться третьей строкой списка, иначе номер бесполезен. Отсюда же дешёвая проверка обоснованности: ссылка на `[7]` при пяти фрагментах — выдумка, и она попадает в лог и в отчёт (ответ при этом не правится: правка чужого текста регуляркой испортит его вернее, чем лишняя ссылка).

*Отказ «в конспектах этого нет» в историю не кладётся.* Предмета разговора он не добавляет, а следующий уточняющий вопрос утянет его в поисковый запрос и испортит выдачу.

### P4. Оценка

Golden set в YAML: вопрос, ожидаемые `lesson_id`, флаг «ответа в базе нет». Встроенные метрики + опциональный RAGAS.

### Провайдеры

```
LLMProvider:       chat(messages, temperature, max_tokens) -> str
EmbeddingProvider: embed(texts) -> vectors;  model_id;  dim
```

v1: `OpenAICompatible` для обоих — ProxyAPI отличается только `base_url`, отдельный адаптер ему не нужен. Фабрика по `LLM_PROVIDER` / `EMBED_PROVIDER`. GigaChat и YandexGPT добавляются файлом в `providers/` без правки ядра; при этом смена **эмбеддера** обязана вести к пересборке индекса — манифест это проконтролирует.

## Верификация

1. **Препроцессинг.** `index build --dry-run` на всех 46 конспектах: гистограмма токенов в коридоре 300–500, вручную просмотреть 10 случайных чанков — у каждого осмысленный `heading_path`, целые предложения на границах, целые блоки кода. Убедиться, что «Дорогой студент!» и «Домашнее задание» отсутствуют, а «Результат дня» и блоки «Актуализация» присутствуют.
2. **Идемпотентность.** Два прогона подряд → второй не создаёт эмбеддингов. Правка одного конспекта → переиндексируются только его чанки.
3. **Защита индекса.** Поменять `EMBED_MODEL` в `.env` → `ask` отказывает с требованием пересборки, а не выдаёт мусор.
4. **Порог и отказ.** Вопрос заведомо вне базы («какая столица Австралии») → отказ, в логах нет вызова LLM.
5. **Фильтры.** Один вопрос с `--lesson PEr06` и без него → в первом случае все источники из PEr06.
6. **Кэш.** Один вопрос дважды → второй `from_cache: true`, время на порядки меньше; `cache stats` растёт. Затем тот же вопрос с другим `--top-k` → кэш **не** срабатывает (доказательство отпечатка конфигурации).
7. **Память.** «Что такое overlap?» → «а сколько его ставить?» → ответ по контексту; `/clear` → тот же уточняющий вопрос уже не понимается.
8. **Провайдеры.** Переключить `LLM_PROVIDER` OpenAI ↔ ProxyAPI → одинаковое поведение, индекс не пересобирается.
9. **Оценка.** `eval run` — отчёт по golden set; `eval run --ragas` в отдельном окружении.

## Что сознательно не делаем

Отдельная модель-реранкер (тяжёлые зависимости ради корпуса в тысячу чанков), гибридный BM25+вектор поиск, расширение запросов через LLM, Telegram или веб-интерфейс (терминал по твоему требованию), облачные хранилища (Chroma локально закрывает объём с запасом), долгосрочная память между запусками.

Каждый пункт — осознанный отказ, а не пропуск: их стоит зафиксировать в README как «возможные направления развития», это сильная часть портфолио.
